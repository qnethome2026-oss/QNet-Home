Use case 2 · urgency: routine

"Hey Home, where are my glasses?"

The calm inverse of a fall. Person-initiated instead of system-initiated, no timers, two or three turns. Every room looks at its own camera with its own vision model, answers in words, and the house replies out loud in the room you asked from.

It exists partly to prove a claim: that adding a whole second capability touches one node module, one skill file, one tool, and three topic names — and leaves the fall path completely untouched.

The flow

The wake phrase is a string comparison

There is no wake-word model. The transcript that Whisper already returned is lowercased, stripped of punctuation, and required to start with "hey home" — with a small edit-distance tolerance so "hey, home" and "hi home" pass. Match, and the remainder is published as a question. No match, and it is discarded, having never left the board.

Why not let the model decide intent?

Someone asking another person "where are my glasses?" must not make the house answer. Requiring a literal phrase is a far stronger filter than asking an LLM to judge whether speech was aimed at it — and letting the model judge would mean a model call on every utterance in the room, putting all household conversation in front of it.

Why not a trained keyword model?

Zero new models to build or train, the phrase is a config string, and it reuses the listen loop that already exists. If it proves trigger-happy, the fallback is a small keyword spotter in front of ASR. Notably not openWakeWord's pretrained weights — they are CC-BY-NC-SA, incompatible with this project's AGPL licence. The code is fine; the weights aren't shippable.

The fall use case doesn't use the phrase at all. During an active session the house has just asked a question, so any speech is treated as the reply. Requiring someone who has just fallen to say a magic phrase would be absurd.

The skill file is the whole difference

---
name: find-object
trigger: kind=query
urgency: routine
---
phases:
  - id: search
    goal: "Work out which room the object is in, then say so plainly."
    tools: [look_in_rooms]
    exits:
      found:     "at least one room reports seeing it"
      not_found: "no room reports seeing it"

  - id: guide
    goal: "They are in the right room but can't see it. Describe where it is
           relative to something obvious nearby."
    tools: [look_in_rooms]
    exits:
      done: "they have found it, or there is nothing more useful to say"

No timers, no on_enter actions. That is the entire difference from the fall skill. Same loader, same engine, same refusal path, same session logging.

"I still don't see them"

A follow-up is a new question, so something has to connect it to the search it follows. The rule is deliberately dumb: the agent remembers the last find result for two minutes. A new question naming no object within that window goes to the guide phase, using the remembered object and whichever room the person is speaking from now. Any question that names an object starts a fresh search.

One variable and one if-statement. No conversation history, no session linking, no cross-room person tracking. Walk to the bedroom, say "I still don't see them", and the bedroom node re-looks in guide mode: "Look left of the lamp, just behind the book."

Honesty when a room doesn't answer

A node can be down, busy running its own vision model, or off the network. The rule: wait up to the configured timeout, then answer with whatever came back — and say what was actually checked.

Because the agent knows how many rooms it expects from house.yaml, it can tell three situations apart. They must not sound the same:

What came backWhat it says
All rooms answered, one found it"They're in the bedroom, on the nightstand."
All answered, none found it"I looked in the kitchen and the bedroom and I don't see them."
Some didn't answer"I looked in the kitchen and don't see them — I couldn't reach the bedroom."

That third row is the one worth building. Silently reporting "not found" when you only managed to check half the house is exactly the kind of thing that makes people stop trusting a system.

These sentences are deterministic — the model never words a search answer. This was decided after watching it fail live: the tool reported no room answered, and the model worded it as "The item is in the living room. The living room camera reported that the item is there." A fabricated location, with a fabricated citation, spoken aloud.

The answer is this skill's safety content, so it moved permanently onto the engine's rails — the same sentence path that the no-LLM mode always used.

Two related rails from the same evening

  • The object is extracted by clause-cutting regex before the model is ever consulted — "where's my X [anything after is noise]".
  • Traffic for rooms not in the configured room map is dropped outright. A coexisting stack on the shared workshop broker was publishing raw speech-to-text chatter as queries.

Latency, and where it goes

Measured, five runs, warm model. Round trip from a client on the board — board → broker → board → frame grab → vision model → broker → board — was 4.13 s median (4.11 / 4.42 min–max). Node-side handling alone was 3.9–5.4 s, of which the vision model call is 3.3–4.5 s.

End-to-end question → spoken answer with one of two rooms responding was 9.4 s, dominated by waiting out the full timeout for the absent room. So the timeout was tuned from 8 s down to 6 s — worst observed 5.4 s plus a margin — cutting that case to ~7.5 s.

The broadcast returns as soon as every configured room has answered, so the timeout is only ever paid for a room that is genuinely silent. Two further design choices keep the number down:

  • Reuse the frame that already exists. The node is already running a camera pipeline for fall detection, so a look takes the latest frame from memory. No second capture path, no rolling buffer. A frame up to a second old is fine for a stationary object.
  • Downscale before the vision model — roughly 640 px, never native resolution. Time-to-first-token grows steeply with input resolution, and downscaling is nearly free. It is the single biggest lever on query latency.

Correlation, because reply topics are shared

Every broadcast carries a query id, and a reply whose id isn't the one just asked is ignored. A late answer to the previous question must never be read as an answer to this one — the kind of bug that produces a confidently wrong answer rather than an obvious failure.

What it can't do, stated plainly

A live look only finds what is currently visible. Glasses in a drawer, under a newspaper, or in a room with no node all produce an honest "sorry, I don't see them."

This is a deliberate v1 choice, not an oversight. The fix is a last-sighting cache, which turns a dead end into "I last saw them on the kitchen counter about an hour ago" — and it is written down as a planned optimisation rather than quietly hoped for.

One measurement window recorded every result as not-found because a teammate was leaning centimetres from the lens. The vision model correctly reported that the queried object wasn't visible. Live camera, live workshop — and the honest failure is the correct behaviour.

Why this capability matters beyond itself

Adding it touched: one new node module, one new skill file, one new tool, three topic names. The engine, the phase loop, the transport, and the entire fall path were untouched.

That is the "one fabric, pluggable skills" claim being demonstrably true rather than asserted — and it is the strongest answer to anyone asking whether this generalises to the next thing a house needs to watch for.
