5. Measured cadence - the honest number (also in measurements.md)
--------------------------------------------------------------------------
qnn-net-run is a CLI: every inference pays process spawn + context reload +
raw file IO on top of the 34.8 ms NPU execute. Measured end-to-end on the board
(110-frame real clip, per-stage wall clock accumulated around each call):

  batch 1:  2.98 fps  (pre 22.7 ms + npu-call 307.7 ms + decode 1.5 ms/frame)
  batch 8: 14.55 fps  (pre  8.9 ms + npu-call  56.9 ms + decode 0.7 ms/frame)
  live camera, batch 1: 2.56 fps (npu-call 339.2 ms)

Batching 8 frames per invocation amortises the ~273 ms CLI overhead 8x and
produced the IDENTICAL single event with identical confidence; it costs up to
8 frames (~0.5 s) of event latency, so batch 1 stays the live default. No CPU
fallback exists in the code - NPU or nothing, as specified.

8. Camera contention finding
--------------------------------------------------------------------------
Checked before touching the device (root lsof + fuser on /dev/video0 and
/dev/video1, plus non-root): NO process held either node - the camera was FREE,
despite three teammate containers running (genai-llm-vlm-service,
qhome-voice-node-main-1, qhome-voice-node-audio-analytics-runner-1). The VLM
container serves Qwen2.5-VL over pre-supplied images on :9001 and does not hold
/dev/video*. vision.py therefore owns the camera per DESIGN §5, and look.py
must consume the /dev/shm frame export, never a second capture.

Related contention that IS real: the NPU. qnn-net-run intermittently failed
(rc=11 once mid-run; once a ~1 min burst of fastrpc "Failed to create
transport for device, error: 1002 / Failed to load skel") while the teammate's
containers were active, with the identical invocation succeeding on manual
retry seconds later. vision.py now retries x3 with 0.2 s backoff and rode
through subsequent runs; a persistent failure still propagates loudly. The
shared-NPU risk is worth knowing for the demo: if the VLM is mid-generation
when a fall happens, the fall inference may be delayed by a retry cycle
(~0.5 s), not lost.
