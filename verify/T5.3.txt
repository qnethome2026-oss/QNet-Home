--------------------------------------------------------------------
PART 0 — WHY NOT PYWEBVIEW (the one design deviation)
--------------------------------------------------------------------
pywebview was tried first, as the brief asked, and it does install
cleanly on this machine (pywebview 6.2.1, pythonnet 3.1.0, both with
arm64-compatible wheels). It cannot create a window. Three attempts,
each failing one layer deeper, which is what makes the conclusion
trustworthy rather than a guess:

  1. Default (pythonnet -> coreclr, .NET 8.0.24):
       clr.AddReference('System.Windows.Forms')
       -> System.IO.FileNotFoundException: Could not load file or
          assembly 'System.Windows.Forms'
     Cause: pythonnet hosted Microsoft.NETCore.App, which has no
     WinForms. Microsoft.WindowsDesktop.App 8.0.24 IS installed, so
     this one is fixable ->

  2. With PYTHONNET_CORECLR_RUNTIME_CONFIG naming
     Microsoft.WindowsDesktop.App: WinForms loads, and after also
     AddReference-ing Microsoft.Win32.SystemEvents, the import gets as
     far as pywebview's EdgeChromium backend:
       from Microsoft.Web.WebView2.WinForms import WebView2
       -> System.TypeLoadException: Could not load type
          'System.Windows.Forms.ContextMenu' from assembly
          'System.Windows.Forms, Version=8.0.0.0'
     Cause: pywebview's bundled WebView2 interop assembly targets .NET
     *Framework*. ContextMenu was deleted in .NET Core 3.0. No amount
     of runtime config fixes a type that does not exist.

  3. So: force .NET Framework instead (PYTHONNET_RUNTIME=netfx).
     .NET Framework 4.8 for ARM64 is present -
     C:\Windows\Microsoft.NET\FrameworkArm64 exists. But:
       clr_loader.get_netfx()
       -> OSError: cannot load library '...\clr_loader\ffi\dlls\
          amd64\ClrLoader.dll': error 0xc1
     0xc1 is ERROR_BAD_EXE_FORMAT. clr_loader ships its native shim
     for amd64 and x86 only; an arm64 process cannot load either.

  Conclusion: on native ARM64 CPython, pywebview needs .NET Framework
  (for the WinForms type) and cannot reach .NET Framework (no arm64
  shim). Not a version pin away - a dead end on this CPU. Recorded in
  qnet/app.py's module docstring so the next person does not spend the
  afternoon re-deriving it.

  Per the brief's own guidance ("packaging existing, working, small
  beats elegant"), the wrapper takes the documented fallback: open the
  dashboard in the system default browser and keep the console alive.
  qnet/app.py keeps open_in_window() as a named, empty seam so a real
  WebView is a one-function change if one ever ships for arm64.

  Two consequences worth naming, both good:
    - the shipped app imports STDLIB ONLY, so the bundle is 20 MB
      instead of ~60 and has no .NET runtime dependency on the target
      machine. A clean-machine install cannot fail on a missing
      WebView2 or Desktop Runtime, because it needs neither.
    - the dashboard itself is untouched. It was already written to run
      from file:// (T5.1), with the broker ws:// URL editable in the
      page, so the wrapper needs to know nothing about brokers.

    %LOCALAPPDATA%\QNetHome before opening it. Under MSIX the payload

    process. Copying 55 KB to the user's own AppData sidesteps that.
    If the copy fails, app.py falls back to opening the bundled file in
    place, so this is an improvement and never a dependency.

      Publisher="CN=QNetHome"                    - must equal the

PART 2 — REPRODUCE
--------------------------------------------------------------------
From the repo root, non-elevated:

    .venv\Scripts\python -m pip install -e .[dev]
    powershell -ExecutionPolicy Bypass -File packaging\build.ps1
    powershell -ExecutionPolicy Bypass -File packaging\make_msix.ps1

build.ps1 wipes dist\QNetHome and build\QNetHome first (a stale onedir
is how a build "passes" while shipping last week's dashboard), asserts
both data files made it into the bundle, and finishes with the
--self-close 5 launch check. Pass -NoVerify to skip the browser tab.
make_msix.ps1 takes -NoSign to stop after packing.

Neither script needs the other's output to be fresh, but make_msix.ps1
refuses to run if dist\QNetHome\QNetHome.exe is absent.

PART 3 — HUMAN CHECKLIST STILL OUTSTANDING
--------------------------------------------------------------------
IMPLEMENTATION T5.3 says "Verify (on a machine with no dev
environment)". This laptop IS the dev environment, so the clean-machine
half of that checklist cannot be self-certified here. Carrying it
forward honestly:

  [x] MSIX builds                    - dist\QNetHome.msix, 8.62 MB
  [x] MSIX is signed                 - self-signed, CN=QNetHome
  [ ] trust the cert                 - ELEVATED, one command:
        Import-Certificate -FilePath .\dist\QNetHome.cer `
                           -CertStoreLocation Cert:\LocalMachine\Root
  [ ] MSIX installs without errors   - Add-AppxPackage .\dist\QNetHome.msix
                                       (blocked only by the line above)
  [ ] app launches from Start menu   - needs the install
  [ ] enter broker IP in settings -> live feed appears, verified
      against an inject                - needs the install + a running
      broker. The dashboard half of this is already covered by
      verify/T5.1.txt and verify/T5.2.txt against the same HTML file
      that is bundled here byte-for-byte (55,414 bytes both sides), so
      what is genuinely unverified is only "does it still work when
      loaded from the packaged path", not "does the dashboard work".
  [ ] uninstall leaves no broken state; reinstall works
        Get-AppxPackage QNetHome.Dashboard | Remove-AppxPackage
      NOTE for whoever runs this: Remove-AppxPackage does NOT delete
      %LOCALAPPDATA%\QNetHome (the staged dashboard copy, ~55 KB).
      Known and documented in SIGNING.md rather than discovered during
      the clean-machine test.
  [ ] clean-machine test              - cannot be done on the build
      machine by definition. The bundle needs no .NET, no WebView2 and
      no Python on the target, which is the main thing that usually
      breaks this step.

All of the above are in packaging\SIGNING.md as copy-pasteable
commands, including how to undo the trust decision afterwards.

Known limitation, recorded rather than hidden: the package is signed
but NOT timestamped, so the signature stops validating when the cert
expires 2027-08-05. A real release adds
  /tr http://timestamp.digicert.com /td SHA256
to the signtool call and uses a CA-issued cert, at which point the
trust step disappears for end users entirely. Not worth doing for a
demo whose certificate is self-signed anyway.
