dashboard/index.html is new. Its whole design premise is one pure function,
humanize(event, ctx) -> {icon, text, tone, badge?} | null, which is the ONLY
path from a wire event to something on screen. Anything it returns null for is
not rendered on this page at all - refusals, llm decision lines, look_in_rooms
and every non-escalating phase move. Those are admin-portal material and the
admin portal still shows every one of them.

Every event kind that appeared in the three replays is accounted for above:
detected, say, heard (silence AND text), phase (escalate / call_help /
resolved / done), tool (notify_contacts / call_emergency / look_in_rooms), and
llm. `brief` and `refusal` did not occur in these three recordings - both are
covered by the synthetic cases in 1a, and both `<hidden>` outcomes in the table
above are the same code path a `refusal` takes.

Two things worth reading off that table rather than glossing over:
  * "A trusted contact was notified" AND "Sarah was notified" both appear.
    That is correct, not a bug: names are learned from what the house says, so
    the very first notify_contacts is humanized before any sentence containing
    "Sarah has been messaged" has arrived. The live page re-renders the WHOLE
    feed on every update, so by the time a human is looking, every line reads
    "Sarah". The generic noun is the guaranteed-English fallback for a house
    whose config was never filled in (config/house.yaml ships "TODO" values and
    a file:// page cannot read YAML anyway).
  * resident=null in this capture, because none of the three recordings
    contained a `brief` line ("... Margaret said ..."), which is where the
    resident's name is learnable from. The page therefore printed
    "Resident: ..." - readable English, no crash, no placeholder token. That is
    the required "must not break if config values are unknown" behaviour,
    observed on real data rather than asserted in the abstract.
