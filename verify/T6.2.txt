Interface change made in this task
-----------------------------------
qnet/tools/ToolContext gained exactly one field, optional and last:

    subscribe: Any = None   # (topic_filter) -> async ctx mgr -> Queue[(topic, dict)]

  Why: look_in_rooms is the first tool that has to LISTEN as well as speak.
  Rather than give tools their own MQTT client (a second connection, a second
  subscription, a second thing to fail), the engine fans its own already-
  dispatched messages out to whoever is listening - Agent.subscribe registers a
  topic-filter queue for the life of an `async with`, and Agent.fanout feeds it
  from on_message. `qnet/+/looked` joined SUBSCRIPTIONS in the same change.
  Compatibility: the field is optional and last, so every existing construction
  site compiles unchanged; a context built without it (tests/test_tools.py's
  five-field make_ctx, unchanged from T2.3) still works, and the tool degrades
  honestly - it broadcasts, reports every room unreachable, and claims nothing it
  did not hear. All 15 tests in tests/test_tools.py still pass.

  Wire-contract note (contracts/mqtt.md): the `look`/`looked` payloads are
  unchanged - this is an internal interface, not a topic. What was added to the
  doc is the timeout's config key (`find.look_timeout_s`), the early-return rule,
  and the qid-mismatch rule, which were prose in §13 and now have a home in the
  machine-referenced copy.

  say.prio gained `routine` (contracts/mqtt.md + DESIGN §4's payload comment).
  A find answer is neither a safety line nor a fall comfort update, and calling
  it `comfort` would corrupt the one prio the comfort-loop soak counts. Nothing
  consumes prio as an enum today (node adapter and dashboard both pass it
  through), so this is an addition: `safety` and `comfort` mean what they meant.

Design ambiguities found and how they were resolved
---------------------------------------------------
1. §13 lists `tools: [look_in_rooms]` in the phase, implying the model calls it -
   but SDK-native tool-calling does not work on GenieX v0.3.18 (§10, measured on
   the board). Resolved: the engine invokes the phase's single allowed tool on
   phase entry, exactly like an on_enter action, and the phase allowlist still
   authorises it (phase.allows_tool, with a `refusal` line if it ever fails).
   The model's job stays what it is everywhere else in this system - wording
   facts the engine already has. Recorded in engine.py's module docstring as
   ambiguity 3.
2. Object extraction order. The task's ladder is heuristic -> LLM -> ask. §13's
   follow-up rule is "an ask that names NO object within the window -> guide".
   Taken literally together, a follow-up would first go to the model, which can
   invent an object out of "I still don't see them". Resolved: heuristic ->
   (nothing named AND the window is live) -> guide -> otherwise the model ->
   otherwise ask. Deterministic on the follow-up path, and one fewer model call
   on the latency-sensitive one. The heuristic also treats a bare pronoun
   ("where are they") as naming nothing, which is what makes that phrasing route
   to guide rather than search for "them".
3. "Ask what to find" opens NO session. A session with no phase to run and no
   timer would sit in the table forever and, by the one-session-per-room rule,
   block the very answer it just asked for ("my glasses"). It is one spoken
   line, on the asking room's topic.
4. The question itself is logged as a `heard` line, not a new log event kind: it
   IS a transcript, so no frozen schema had to change and the dashboard renders
   the find timeline with no change at all.
5. `last_find` is house-wide, not per room - the whole point of the follow-up is
   that they walked into the other room. Refreshed on every completed search or
   guide.
6. Wording avoids is/are on the object entirely ("I found your glasses ..." /
   "I found your phone ...") so nothing has to guess whether a spoken noun is
   plural.
