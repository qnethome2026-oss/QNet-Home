=== Decisions worth flagging for the engine integration (T2.2/T3.x) =======

1. ToolContext.log is documented as a SYNC callable
   ("log: Any  # (event: dict) -> None") while Agent.append in
   qnet/agent/engine.py (T1.3) is async (it awaits self.publish after the
   file write). Every tool here calls `ctx.log(...)` synchronously, per the
   given interface. Whatever the engine wires as ctx.log for a real session
   needs to be sync-callable from a tool's perspective - e.g. a small
   non-async wrapper that appends to session.log and the file, and schedules
   the qnet/session/<id> publish separately (or the engine calls ctx.publish
   itself around the tool call). This repo's ToolContext.publish is separately
   available (async) for anything a tool needs to put on the bus directly -
   none of the four tools currently use it themselves; all consequential
   bus traffic for these two (notify/emergency) stays off MQTT entirely, by
   design (§11: emergency call is simulated, notify only goes to Telegram).

2. notify_contacts sends to EVERY contact in house.yaml's `contacts:` list
   that has a real (non-TODO) telegram_chat_id, not just the first one. With
   today's house.yaml (one contact, "Sarah") this is unobservable, but if a
   second contact is added, both get messaged. `delivered` is True only if
   ALL sends succeeded; a partial failure reports delivered=False/console
   even though some contacts *did* get the message - the outbox log has the
   text either way. Flagging in case the engine wants per-contact delivery
   detail later (not in this tool's return shape today).

3. get_session_summary's "current/final state" is INFERRED, not read off an
   explicit field - see the module's docstring in
   qnet/tools/get_session_summary.py for the full reasoning. Short version:
   contracts/mqtt.md's six JSONL line kinds (detected/say/heard/phase/tool/
   refusal) have no explicit "session ended" line. This tool takes the last
   `phase` event's `to` field and treats it as a phase-jump if it's one of
   {check, escalate, call_help} (state stays "active"), or as a terminal
   label otherwise (state = that label, e.g. "ok"/"resolved"/whatever the
   T2.2 cancel path logs). If T2.2 lands a different, more explicit way to
   mark closed/cancelled in the JSONL, this is the one place to update -
   KNOWN_FALL_PHASES and the inference block, both near the top of the file.

4. call_emergency's output filename is `emergency_<epoch-ms>.json`
   (millisecond integer, not a formatted timestamp) specifically so two
   calls within the same second never collide - relevant if a test or a
   demo run fires it more than once quickly.

5. Every tool is wrapped so it truly cannot raise, including the FALLBACK
   paths: printing a Telegram template with emoji to a real Windows console
   (cp1252) raises UnicodeEncodeError from plain print() - caught the first
   time in testing this file's own demo script, not in a unit test. Fixed
   with qnet.tools.console_print (a print() that retries ASCII-safe on
   UnicodeEncodeError), used everywhere qnet/tools/*.py prints anything to
   stdout. Covered by test_console_print_never_raises_on_narrow_console.
   Worth the engine integrator knowing about if any other on-console logging
   is added near these templates.

6. look_in_rooms's stub `unreachable` list is simply
   `list(config["rooms"].keys())` - with today's house.yaml (only "kitchen"
   configured) that's `["kitchen"]`; it will show every configured room once
   bedroom/etc. are added, which is the point (T6.2 replaces the body, not
   the signature).
