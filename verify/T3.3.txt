=== prompt calibration - what was measured, not guessed ================
Every "obviously helpful" sentence was A/B'd on the live model before shipping,
5 replays per reply, same options, temperature 0 (see "surprised us" #1):

  arm                                   first-question set   pain double-check
  bare (role+goal+asked+exits+heard)          44/45  <-- shipped     20/25
  + "if unsure, choose escalate" tail         41/45                    -
  + "ok does not close anything" note      25-26/30                    -
  + pain polarity note                          -            24/25  <-- shipped
  restructured prompt (heard before exits)    30/36                  17/20
  option order (escalate, ok)                 37/40         (ok, escalate) 40/40

  Shipped: the bare template, plus ONE sentence during the pain double-check -
  `Note: "no" or "nothing" here means they have no pain and did not hit their
  head.` It exists because fall.md's escalate condition literally reads "they
  say no", while a "no" to *"any pain?"* is the reassuring answer; without it
  the model escalated the demo's closing line 5 times out of 5.

=== the other phase the model sees: `escalate` =========================
The scoreboard is all `check` (that is where the consequential decision lives).
`escalate` offers one exit, so its option set is (check, wait) - "did they
respond coherently enough to go back and reassess?". Measured, 3 replays:
  "i'm still here" 3/3 check   "yes" 3/3 check   "i'm okay now" 3/3 check
  "it hurts" 3/3 check   "how long will it be" 2/3 check   "asdf gwqk" 3/3 wait
  ...but a repeat batch an hour earlier scored the same set 13/18 (see #1).
A wrong `wait` here is mild: the comfort loop keeps talking and the 15 s timer
still carries the session to call_help. `call_help` gets NO model call at all -
its only exit is "a responder has arrived", which is not a claim a transcript
can support (llm.options_for returns nothing there, so no request is made).

=== what surprised us about the live model =============================
1. Temperature 0 is NOT deterministic on this stack. The same prompt, same
   request, minutes apart, flips on borderline replies. Everything here is
   therefore reported as a rate over repeated runs, not a single observation -
   and the engine treats a model answer as a suggestion, never a guarantee.
2. More instruction made it worse, consistently. Adding the design's own
   "ambiguity resolves toward help" sentence to the prompt dropped "I'm fine"
   from 5/5 to 2/5 - a 2B model weights the last thing you tell it hardest, and
   the rule was already enforced where it belongs (engine.classify_reply).
3. Off-topic ("what time is it") is the model's genuine coin-flip: it sometimes
   answers `ok`. Benign by construction - `ok` at the first question buys the
   canned pain double-check, not a close, and the 30 s phase timer keeps
   running underneath - but it is why the bar is 9/10 and not 10/10.
4. `nctx: 16384` per request is accepted and harmless (T3.2 residual: grep nctx
   qnet/agent/llm.py). No reload, no slowdown, no crash.
5. Classification is far cheaper than the setup log's 16 tok/s suggests: the
   answer is one token, so a turn is essentially TTFT + prefill (~0.5 s).
6. Requests really do serialize. One suite run failed mid-way when the device
   was busy with someone else's generation: the 6 s client timeout fired, the
   retry timed out too, and the turn fell through to the regex classifier -
   which escalated correctly. Degraded, not broken, exactly as §6 promises.
   Live-test waits were widened to 40 s afterwards; the client timeout stayed 6 s.
