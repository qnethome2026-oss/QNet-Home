# Maker / Home-Lab Builds Scan — Camera+Mic+LLM+Speaker+Home Combos
**For:** QNet Home @ Snapdragon Multiverse Hackathon (Aug 3-7 2026)
**Purpose:** hunt real maker/hacker builds (Frigate+LLM rigs, HA VLM automations, talking houses, kid/pet monitoring, tiny-board LLMs, ESPHome voice satellites) to mine for WOW demo beats that prove QNet Home's crux: **privacy-by-construction (semantic JSON only, no video/audio leaves the edge), multi-device fabric (PC hub + phone + Arduino UNO Q + AIC100), agentic in-room voice response.**

Research method note: live web search quota was exhausted for this session; all findings below were gathered via targeted page fetches (DuckDuckGo/Bing HTML result pages + direct fetches of GitHub/Hackster/Hackaday/community.home-assistant.io/vendor doc pages). Numbers and quotes are as reported on those pages, not independently re-benchmarked.

---

## 1. Frigate + LLM/VLM combos (the closest analog to QNet Home's core loop)

This is the single most mature "maker did our thing already" cluster — it validates that judges and the maker crowd already recognize and reward exactly the pattern QNet Home is built on: **camera → local vision-language description → structured event → speaker/notification**. QNet's differentiator has to be that it *never* sends the pixels anywhere, whereas every one of these still snapshots a JPEG into an LLM.

- **Frigate native GenAI (docs.frigate.video/configuration/genai)** — Frigate (the most popular open-source NVR, blakeblackshear/frigate) now ships first-class GenAI config. Supports local models via Ollama (**qwen3-vl, qwen2.5-vl, InternVL3.5, gemma3**) or cloud (Gemini free tier, GPT-4o, Azure OpenAI). Generates two artifacts per event: an **object description** and a **Review Summary** (a natural-language digest of a whole review window, not just one clip). Sizing guidance given: 8 GB RAM for 7B models, 16 GB for 13B, 32 GB for 33B; explicit warning that Ollama CPU-only is "impractical" — GPU/NPU is a hard requirement for usable latency. Docs recommend **instruct** variants over "thinking" variants because thinking models ramble instead of emitting the terse actionable description Frigate wants.
  - → **QNet beat (wow: high / feasibility: high):** This is direct proof the crowd already validates "VLM turns camera event into text." QNet's pitch line becomes: *"Frigate does this and phones the JPEG to Ollama or GPT-4o. QNet Home does the identical inference on-NPU and the frame is deleted from RAM before the JSON event is even serialized — nothing but semantic text ever leaves the device."* Consider literally logging a Frigate-style description JSON side-by-side with QNet's semantic event schema on a judge-facing screen with a big "❌ image bytes: never transmitted" badge.
  - **Pitfall to flag for our own build:** the "Review Summary" concept (rolling digest of many events into one narrative) is a nice feature we don't have yet — a caregiver-app "what happened while you were out" paragraph generated from the accumulated semantic event log, zero extra vision inference needed since it's just summarizing JSON we already have. Cheap to add, high perceived intelligence.

- **HA-LLMVision / "llmvision.org"** (github.com/valentinfrlch/ha-llmvision, ~1.4k GitHub stars, active Discord) — Home Assistant integration analyzing images/video/live feeds/Frigate events via any multimodal LLM (OpenAI, Anthropic, Gemini, Bedrock, Azure, Groq, Ollama, LocalAI, any OpenAI-compatible endpoint). Notable features: **cross-analysis memory of specific people/pets/objects**, a dashboard **Timeline** card, and the ability to **query the timeline through HA's voice assistant** ("what happened at the front door this morning?").
  - → **QNet beat (wow: high / feasibility: medium):** The "ask your voice assistant about the timeline" pattern is exactly the caregiver two-way-voice interaction QNet already plans, but LLMVision proves it's a demoable, judge-legible beat: *live voice Q&A over the day's semantic event log* ("Hey QNet, did anyone go into the garage after 9pm?"). Worth scripting explicitly as a demo beat — it's cheap (just RAG over the JSON event stream we already produce) and it visibly shows the "agentic in-room response" pillar.

- **Community thread "Camera + Frigate: Intelligent AI-Powered Notifications"** (community.home-assistant.io/t/785335, 21 likes) — MQTT/entity-triggered notifications with LLM-written summaries instead of "Person detected." Feedback thread shows real friction points makers hit: (a) users want triggering from generic motion sensors, not just camera-state-change, because some NVRs (Unifi Protect) stream constantly; (b) Ollama calls **blocked the HA event loop** until fixed; (c) Docker networking/SSL was the #1 support burden.
  - → **Pitfall for us:** blocking inference calls stalling the automation loop is a known failure mode — make sure QNet's NPU inference call is async/non-blocking relative to the event bus, or a demo hang will read as "broken," not "thinking."

- **Ambient Node "Using AI Vision and Voice with Home Assistant"** (ambientnode.uk) — explicitly framed around **local-only** Frigate + Ollama + custom reverse proxies for a fully private pipeline, no cloud calls at all.
  - → **QNet beat (wow: medium / feasibility: n/a-comparison):** Good citation for "the local-only camp exists and is a known-good practice," but it's still image-based (snapshots stored/inferred), reinforcing that QNet's *image-never-leaves-the-sensor-and-is-discarded-post-inference* stance is one step further than the current state of the art in this space — a genuinely defensible technical differentiator to state explicitly in the pitch.

- **Frigate two-way talk (docs.frigate.video/configuration/live)** — WebRTC-based bidirectional audio to ONVIF Profile T cameras with speakers (Reolink doorbells etc.). Docs confirm this is a *pure AV relay* feature (you literally talk into your PC mic) — there is **no built-in AI-generated speech integration** yet. That gap is wide open.
  - → **QNet beat (wow: very high / feasibility: high, this is close to what's already planned):** The crowd has the hardware pattern (speaker in every room, WebRTC talkback) but nobody has wired an *LLM-authored, context-aware* utterance into it as a default behavior — they only support human-relayed speech. QNet's "hub speaks proactively into the room, with barge-in two-way voice" is the feature the entire Frigate/HA ecosystem is visibly missing and asking for indirectly (see the PaLM item below, which hand-rolls exactly this outside Frigate).

## 2. HA + VLM "smart" home-safety automations already built by real users

- **StoveML / "is the stove on"** — makers have built custom CV classifiers pointed at the stove (camera + custom ML model → HA boolean state), separate from LLM Vision's more general appliance-left-on monitoring; parallel low-tech competitor is smart-outlet/gas-valve auto-shutoff hardware (e.g. YoLink gas valve). One maker uses plain OpenCV to read the *illuminated burner indicator light* rather than the burner itself — a nice reminder that sometimes a tiny heuristic beats a VLM call.
  - → **QNet beat (wow: medium / feasibility: high):** "Is the stove on" is a great **elder-safety** semantic event type for QNet (`appliance_left_unattended`, room = kitchen, duration_threshold) — trivially fits the existing semantic-JSON schema, no new vision capability needed beyond what a VLM tier already gives (object + state description). Cheap addition to the elder-care demo track alongside fall/wander.

- **AI Package Detector Blueprint** (community.home-assistant.io/t/846591) and **ha-package-vision** (github.com/alexnorell/ha-package-vision, built on Roboflow Inference) — dedicated package-on-porch detection distinct from generic person detection.
- **Reolink-camera-with-TTS** (markus-haack.com "making your reolink camera talk") — motion → AI analysis → **TTS announcement straight out of the camera's own speaker**, no separate smart speaker needed.
- **AI Presence Announcer** (github.com/AllenSikorski/ai-presence-announcer) — Ubiquiti AI camera → HA → **Node-RED** → **MQTT** → a $ cents **ESP32 + DFPlayer MP3 module** wired to a whole-property PA system, so *any* zone can broadcast a chime/voice announcement. Explicitly supports "known vs unknown person" branching logic and manual physical-button override.
  - → **QNet beat (wow: high / feasibility: high):** This is basically a cheap, crude version of QNet's "speak into rooms" fabric, minus the semantic privacy layer and minus any real NLG (it plays canned MP3s, not generated speech). Good proof point: *"makers already wired whole-house PA announcement systems off of AI camera events with $10 of ESP32 hardware — QNet does the same fan-out but the payload is a locally-generated, context-specific sentence from an SLM, not a static MP3."* Also a legit hackathon shortcut if we need a *cheap redundant audio-out channel*: an ESP32 + small amp + MQTT subscriber is a same-day build if a room's "official" speaker device fails during the demo.

- **"PaLM Speech Engine" — LLM-rewritten Jarvis-voice announcements** (community.home-assistant.io/t/611011, 5 likes but conceptually the sharpest find of the scan) — Sends every canned TTS announcement through an LLM with a hard-coded personality prompt ("intelligent, witty, sarcastic, dark humor — like Jarvis") before speaking it, via HA's `conversation.process` service. Result: the same event ("coffee ready") produces a *different, personality-consistent* sentence every time instead of a robotic repeat.
  - → **QNet beat (wow: very high / feasibility: high — literally just a prompt template around the SLM call you already have):** This is the single highest-leverage cheap WOW upgrade in the whole scan. QNet Home already plans TTS + cloned-parent-voice; layering an LLM rewrite step (not just template-filling) between the semantic event and the TTS text means **the same "child near stove" event never sounds the same twice, and can carry tone appropriate to the room/persona** (calm-firm for a kid's room in the cloned-parent voice, neutral-factual for the caregiver phone card). Directly demonstrates "agentic in-room response" rather than "notification with a voice skin," and it's near-zero engineering cost if the SLM pipeline already exists — just add a persona system prompt keyed by room/profile before the TTS call. This should go straight into the demo script.

- **Proactive conversation thread** (community.home-assistant.io/t/891739, "Initiating a conversation by proactively asking a question") — real users asking HA's forum how to make Assist *initiate* dialogue rather than only respond, confirming this is a known unsolved itch in the ecosystem.
  - → **QNet beat:** validates that "hub proactively opens a two-way voice exchange" (not just announces) is a differentiator judges in this space would recognize as advanced — worth a dedicated demo beat: hub detects an ambiguous event (e.g., unknown motion at 2am), *asks* the room "Is someone there? Should I call [caregiver]?" and waits for a barge-in-capable reply before escalating.

## 3. Wildlife / pest / porch-pirate voice-deterrent builds

- **Raccoon/opossum-specific Frigate blueprints:** could not find a dedicated, well-documented "Frigate detects raccoon → speaks" build in this pass (search budget/engine limits — see Sources note); general Frigate label detection (Frigate+ ships wildlife labels) plus the generic notification blueprints are the closest evidence, meaning this exact demo ("critter cam yells at raccoon") is *underbuilt* relative to how often it's discussed — an actual opportunity gap rather than a saturated bit.
- **Porch-pirate "AI can tell a thief from a delivery driver" marketing pieces** (Las Vegas / San Antonio local-news coverage of commercial products, plus viral **AI-generated fake** porch-pirate "instant karma" videos that fooled news outlets during 2025 holidays) — confirms strong public appetite for "camera talks back to the bad guy," but the *real* documented technical implementations are thin; most of what's viral is AI-generated fiction, not an actual running system.
  - → **QNet beat (wow: high / feasibility: medium):** There's a genuine crowd-pleaser gap here: a **real, on-device, zero-cloud** "stranger lingering at door → SLM composes a firm spoken warning → speaks it live" demo would visibly outperform the vaporware/viral-fake pieces currently dominating this topic, and ties cleanly to the "no video ever leaves the device" privacy pillar (unlike commercial doorbell-cam AI that clips and uploads).

## 4. Pet AI: deterrents & bark/sound analysis

- **AI Cat Deterrent Automatic Sprayer** (hackaday.io/project/176806, Raspberry Pi Zero W + NoIR cam, AI facial recognition of the cat's own face, servo pan/tilt, 12V washer-motor sprayer) — modest traction (2.3k views, 2 likes, 5 followers) and the maker's own log calls out **"a very slow camera feed from my Pi Zero W"** as the practical bottleneck — i.e., real people hit real latency walls on Pi-class hardware for this exact "detect → react in real time" loop.
- **Cat-Turret** (github.com/EngineerGuySam) — Pi 4 + YOLO + servo aim + water pump, counter-jumping deterrent.
- **CritterTurret / PetHunter** (YouTube, Raspberry Pi 5-based squirt-gun turrets for wildlife/pet deterrence) — Pi 5 chosen specifically over Pi 4/Zero for the vision throughput.
- **Bark Back** (SparkFun tutorial) — Pi + MEMS mic, plays the *dog's own recorded bark back at it* to interrupt barking loops (no AI classification, just noise-threshold trigger — a reminder that not everything needs an LLM).
- **Dog Emotion Translator** (github.com/BarathElumalai22/dog-translator-ai) — classifies bark audio into happy/sad/alert/normal emotional states.
- **"AI Noise Analyzer"** (projects-raspberry.com) — Coral Dev Board / Pi4 + Edge TPU, 24/7 ambient sound classification including dog barks, fully local.
  - → **QNet beat (wow: medium-high / feasibility: high, and cheap):** Pet/kid-adjacent sound classification (bark type, distress cry, glass break, snore/apnea-adjacent) is a **non-camera, audio-only semantic sensor** that's maximally aligned with QNet's privacy pillar (classify locally, emit one word like `bark:alert`, discard audio) — see the Seeed module below, which productizes exactly this. Good candidate for a second sensor modality beyond vision-per-room, to visually demonstrate "multi-modal fabric," not just "camera network."
  - **Pitfall confirmed twice independently (Pi Zero W log + general Pi Zero/4 pattern):** low-end ARM boards choke on continuous frame-by-frame vision loops. Directly relevant to the UNO Q (QRB2210, 4×A53, Adreno GPU, **no NPU**) — do NOT plan continuous per-frame VLM inference on the UNO Q node; use it as a lightweight motion/heuristic pre-filter (OpenCV/YOLO-tiny on GPU) that only *wakes* a room-level event, with the actual semantic description happening on a device that has an NPU (phone or hub), or batched/low-fps.

- **Seeed XIAO ESP32-S3 + XU316 AudioEventSensor "Sound Event Detection Module"** (wiki.seeedstudio.com) — a genuinely notable, close-to-productized find: a **$10-class module** that detects **baby cry, glass break, gunshot, alarm (T3/T4), and snore** entirely on-device via UART/AT-commands into ESPHome, explicitly marketed on "strong local data privacy protection" (raw audio never leaves the sensor — only an event class + confidence 0-100%).
  - → **QNet beat (wow: high / feasibility: high — this is basically a plug-and-play edge node for QNet's exact philosophy):** This is the single closest commercial artifact to "QNet Home's philosophy, productized" that turned up in the whole scan — a cheap microcontroller doing local audio classification and emitting only a semantic event, matching QNet's edge-node contract almost exactly. Strongly consider **buying one or two of these for the demo table** (if orderable in time) as a "look, the industry is already validating our exact edge-node contract — here's a $10 chip doing it" prop, or at minimum cite it explicitly in the pitch deck as third-party validation of the privacy-by-construction pattern. Also directly gives us a ready-made **glass-break / gunshot / distress-cry** event type to add to the taxonomy without building new ML.

## 5. Kid-monitoring automations parents actually built

- **Mac Screen Time Enforcer** (github.com/040medien/mac-screentime-enforcer) — controls a kid's Mac screen time through Home Assistant schedules/automations (bedtime, school-hours, homework-first rules) — no vision, just device/network-layer enforcement.
- **KidsChores and Rewards Dashboard** (HA community) — full chore/rewards system with parent-approval workflow, badges/streaks/challenges.
- **ChoreSplit** (choresplit.com/ai) — **photo-based AI verification of completed chores** ("photo verification in seconds") plus AI-generated task/project lists — this is the closest thing found to actual vision-based chore verification.
- **"AI Camera Curfew Enforcer"** (YouTube, n8n + Frigate) — Frigate person detection wired through n8n workflow automation to enforce a family curfew.
- **"Child Safety with Location & AI Monitoring"** (resonatetoinnovate.com) — combines GPS geofencing + AI camera detection + custom automation for child safety, i.e. a real-world precedent for fusing *phone location* with *home camera events* the way QNet's caregiver-phone-app pillar already intends.
  - → **QNet beat (wow: medium / feasibility: high):** "Chore verification via photo → AI confirms done" (ChoreSplit) is a fun, low-stakes, high-relatability demo beat that's easy for judges to grok instantly ("did the kid actually clean their room?") and reuses the exact same VLM-description pipeline as the safety events — good comic-relief beat between the more serious elder-safety scenarios, and it reinforces "semantic-only" (event = `chore_verified: true/false`, no photo retained).
  - **Differentiator to state explicitly:** none of these fuse *curfew + geofence + in-home camera + voice* into one *cross-device* pipeline the way QNet's phone+hub+edge-node fabric can — the resonatetoinnovate piece is closest but reads as a blog concept, not a working repo. This is a legitimate "nobody's actually stitched all four together" claim.

- **HA community "elderly person fall alarm" thread** (t/659804) — real users explicitly asking for affordable **local** fall-alarm hardware and struggling to distinguish genuine falls from normal movement — i.e., false-positive tuning is a known, unsolved pain point the crowd is vocal about.
- **Eiko** (hackster.io/548780) — "companion robot for lonely elders," vision-based emotion/gesture sensing framed as turning "passive care into active, heartfelt connection" (page fetch blocked by 403; description from search snippet only).
- **Aigis** (hackster.io/Varun_Sontakke) — "AI Family Guardian & Smart Home Companion" built on an **ESP32-S3-BOX-3**, offline speech recognition, wireless mesh networking, health monitoring (403-blocked for detail; snippet-level only).
- **Sunny / elder-companion** (github.com/cottonandcolor/elder-companion) — warm voice companion for elderly living alone, powered by **Gemini Live API** (cloud, not private — useful negative example).
- **HelpGranny** (github.com/rafaym1/HelpGranny) — an agent that "taps, scrolls, types, and navigates like a grandkid sitting next to her," aimed at helping elderly users operate phones and **avoid scams** — a genuinely different angle (assistive UI agent, not a monitoring sensor).
  - → **QNet beat (wow: very high / feasibility: medium):** The fall-detection cluster confirms the false-positive/false-negative tuning problem is real and judged — if QNet demos a fall/wander scenario, explicitly show the **confidence threshold + escalation ladder** (local chime → room voice check-in → caregiver phone ping → emergency contact) rather than a single binary alarm, since that ladder is exactly what the HA crowd says they're missing. The Gemini-Live-powered "Sunny" project is a good **explicit contrast point** in the pitch: "elder companion projects today default to cloud LLM APIs (Gemini Live) with always-on audio streaming to Google — QNet's equivalent runs the SLM on-device and never streams raw audio anywhere."
  - **HelpGranny's "scam prevention via phone agent"** is an interesting adjacent-but-different WOW: not in QNet's current scope, but if there's spare build time, a **"grandma just got a call from a fake grandchild asking for gift cards — QNet's in-room voice notices anomalous financial-sounding conversation cues and proactively checks in"** scenario would be a novel elder-safety beat nobody else in this scan has built as a *home-ambient* (vs. phone-agent) pattern. High wow, but feasibility is speculative/risky for a 4-day build — flag as stretch-goal only if core demo is solid early.

## 7. Tiny-board VLM/LLM performance data (UNO Q-class and PC-hub-class reality check)

- **SmolVLM2** (HF blog) — 2.2B / 500M / **256M** parameter video-language models, explicitly pitched as running inside a free Google Colab and locally on an iPhone (500M variant, MLX). No hard fps numbers surfaced in this pass, but confirmed as the smallest publicly-marketed "video-capable" VLM family — a candidate for the absolute-lowest-tier fallback model if the UNO Q ever needs to run inference itself rather than just relay to the hub.
- **Moondream** (github.com/vikhyat/moondream) — 2B and **500M** parameter VLM family, explicit capabilities: captioning, VQA, and **object detection with pointing** (not just bounding boxes — can answer "point at the stove knob"), positioned as "runs anywhere," resource-constrained-hardware target.
  - → Both are good "spare tier" model citations if QNet wants a documented fallback VLM below its main Qwen3-VL tier for degraded/offline nodes.
- **FastFlowLM Qwen3 NPU benchmarks** (fastflowlm.com/docs/benchmarks/qwen3_results) — concrete numbers, though measured on an **AMD Ryzen AI 7 350 NPU**, not Qualcomm Hexagon (still useful as an order-of-magnitude sanity check for Qwen3 tiers):
  - Qwen3-0.6B: **66.5 tok/s decode** at 1k context, dropping to 14.1 tok/s at 32k context; prefill 2,165 tok/s at 4k prompt.
  - Qwen3-8B: **11.9 tok/s decode** at 1k context down to 7.2 tok/s at 32k; prefill 457 tok/s at 4k prompt.
  - **Qwen3-VL-4B image TTFT: 3.3 seconds at 720p, ballooning to 41.2 seconds at 4K.**
  - → **Critical, concrete pitfall for QNet's own pipeline:** VLM time-to-first-token scales brutally with input image resolution — a **~12x latency blowup from 720p to 4K** on comparable NPU-class silicon. If any QNet edge node feeds full-res camera frames into the VLM tier, this alone could tank the "measured latency" judging criterion (Technical 40 pts explicitly rewards latency numbers). **Action: downsample every frame to ≤720p (or lower) before VLM inference, and put this decision + the before/after latency number directly on a judge-facing dashboard** — "we measured this, and pre-resize saved Xx." That's a real, citable engineering decision with a number attached, exactly what the Technical rubric wants.
- **Arduino UNO Q hardware confirmation** (docs.arduino.cc/hardware/uno-q) — Qualcomm Dragonwing QRB2210, quad-core Cortex-A53 @ 2.0GHz, Adreno GPU, dual ISP (13MP+13MP or 25MP @ 30fps), 2GB/4GB RAM variants, Debian Linux + companion STM32U585 MCU (Cortex-M33 @160MHz) for real-time I/O via an RPC bridge. Docs confirm **no dedicated NPU** — matches the brief. No official GStreamer-specific AI demo found in docs (general "AI at the edge" framing only); community coverage so far is limited to basic YOLOv4-tiny object-detection smoke-tests, nothing production-grade yet.
  - → **QNet beat (wow: medium / feasibility: confirms existing plan):** Since the UNO Q has zero NPU and (per the Pi-Zero/Pi4 pattern above) ARM A53-class CPUs choke on continuous per-frame vision, the UNO Q's best role in the fabric is almost certainly: (1) GStreamer-native camera/mic capture + lightweight motion/VAD gating on CPU/GPU, (2) emit a cheap "something happened" trigger over the network, (3) let a real NPU (phone or PC hub) do the actual VLM/SLM inference on a *cropped, downsampled* frame pulled on-demand — never a sustained local inference loop. This is also a clean way to visibly show "heterogeneous fabric, each device doing what it's good at" for the Innovation/Deployment judging criteria, rather than every node doing the same thing.

## 8. Voice satellite ecosystem (ESPHome / Wyoming) — what a $10-60 device does vs. the PC hub

- **Home Assistant Voice Preview Edition** (home-assistant.io/voice-pe) — **$69**, ESP32-S3, XMOS XU316 audio DSP, dual-mic array, 3.5mm out, wake words "Okay Nabu / Hey Jarvis / Hey Mycroft." Two local STT tiers: **"Focused Local"** (Speech-to-Phrase, runs on very low-end hardware, fixed-phrase-only) vs **"Full Local"** (real Whisper, needs Intel-N100-class compute) — i.e. the *reference open voice-assistant hardware* explicitly splits "cheap but limited" vs "capable but needs a real compute hub," which is precisely QNet's own edge-node/hub split, and a clean analogy to cite.
- **Wyoming protocol / wyoming-satellite** (github.com/rhasspy/wyoming-satellite) — the standard streaming protocol that turns *any* small device (Pi Zero 2W, ESP32-S3-BOX-3, even a repurposed PC) into a voice endpoint that streams raw audio to a central server for STT/TTS/NLU — confirms the industry-standard architecture is "dumb thin capture node + smart central brain," reinforcing QNet's hub-centric design as the correct, currently-standard pattern (not a shortcut).
- **Device price/capability ladder documented** (smarthomeexplorer guide, 2026): ESP32-S3-BOX-3 ($60, on-chip wake-word NPU before streaming to server) → Pi Zero 2W kit ($65, <2W idle) → ReSpeaker 2-Mic Pi HAT ($40) → M5Stack Echo Pyramid ($40) → Anker PowerConf S3 repurposed speakerphone ($130) → Pi 5 8GB as an all-in-one server+satellite ($200, runs Whisper+Piper locally). **Every one of these treats voice capture/output as a commodity endpoint and pushes all "intelligence" to a central server** — exactly QNet's hub-does-the-thinking model, at prices as low as $40.
  - → **QNet beat (wow: medium-high / feasibility: high, cheap insurance):** If time allows, wiring one $40-60 ESP32-S3 Wyoming satellite as an *additional* "room" beyond the primary demo rooms would (a) prove the fabric scales to trivially cheap nodes, not just the flagship Snapdragon kit, and (b) is a battle-tested, well-documented integration path (Wyoming protocol) rather than something built from scratch under time pressure — lower risk than it sounds. Even just *namechecking* Wyoming/ESPHome compatibility as "QNet's event bus is protocol-compatible with the existing $40 open voice-satellite ecosystem" is a strong Deployment-score line (20 pts) — shows real-world integration path beyond the demo rig.

## 9. Multi-camera person re-identification / cross-room tracking

- **multicam-reid** (github.com/kunalg06/multicam-reid) — most complete community implementation found: per-camera `CameraWorker` processes → central SQLite `IdentityStore`, **MobileNetV3-Small** (512-d embeddings, L2-normalized cosine match, EMA update `0.7*old+0.3*new`) explicitly chosen over torchreid because torchreid's Cython build breaks on modern Python — a real, practical engineering note. Ships a **"Lost Person Registry"**: anyone unseen for 120s (configurable) flips to LOST but stays permanently matchable — if they reappear on *any* camera weeks later, the same identity re-attaches and a reappearance event fires. Streamlit ops dashboard: live overview, active/lost lists, per-ID timeline, search by ID/time/camera. Original academic baseline (YOLOv4+DeepSORT+torchreid) scored **IDF1 50.7%, MOTA 99.8%**; this reimplementation modernizes to YOLOv8+ByteTrack but doesn't republish the metric.
- **Multi_Camera_Tracking** (github.com/Adigateway) — projects multi-camera detections into a unified top-down floor-plan view.
- Jetson-class variants (Human-ReID-in-NVIDIA-Jetson, Smart-Human-Detection-Recognition-System with TensorRT, NVIDIA's own "homesecurity" Jetson community project) confirm this workload is routinely run on Jetson Nano/TX2-class edge compute, i.e., comparable compute tier to what a PC-hub-class NPU should handle easily.
  - → **QNet beat (wow: very high / feasibility: medium-high, and this is the single biggest "prove the multi-device fabric" opportunity in the whole scan):** A **cross-room "where is grandma / where is the kid" identity thread**, stitched from *semantic* per-room events (not shared face embeddings or video) is precisely the multi-device-fabric crux judges are told to look for. The re-ID crowd's own architecture is the blueprint: keep a lightweight **"Lost/Active Person Registry" state machine** but feed it from QNet's *already-private* per-node person-attribute events (e.g., `person: {height_class, clothing_color, room, timestamp}`) instead of face/body embeddings — this gets 90% of the "the house knows where everyone is across rooms" wow with **zero biometric data ever computed or transmitted**, which is a strictly stronger privacy story than every re-ID project surveyed (all of which move embeddings, i.e. quasi-biometric vectors, across the network). This should be pitched as *"privacy-preserving re-identification via coarse semantic attributes, not embeddings"* — a genuinely novel technical claim if it isn't already in the QNet spec.
  - **Adopt directly, cheaply:** the "Lost Registry never deletes, re-attaches on reappearance" state-machine idea, and the live ops dashboard concept (could become the caregiver app's home screen: active semantic "who's where" + history).

## 10. Miscellaneous notable finds

- **Baby cry detection cluster** — several independent boards (ESP32-S3 FireBeetle2, ESP32-CAM+INMP441, Arduino Nicla Voice via TinyML/Edge Impulse with **synthetic training data generated by ChatGPT**) all converge on the same idea: cheap mic-only local classifier, no camera, no cloud. The "TinyML baby-cry detection using ChatGPT + synthetic data" project (hackster.io/shahizat, 403-blocked for full detail but confirmed via snippet) is notable as a **novel data-generation trick**: use an LLM to synthesize labeled training examples for a tiny audio classifier instead of collecting real recordings — could be relevant if QNet needs to quickly bootstrap a new local event-classifier class (e.g., "distress cry" or "raised voices") without a real dataset in 4 days.
- **Arduino Uno Q community coverage** is still thin (board just launched ~Oct 2025 per Arduino blog date found) — being an early adopter of this exact board for a *coherent, working, multi-node privacy fabric* demo is itself a novelty/wow point almost by default, since there's essentially no prior art to be compared against unfavorably.

## Ranked Top 10 — highest-leverage ideas for QNet Home

1. **LLM-authored, persona-tinted TTS layer between semantic event and speech** (from the "PaLM Speech Engine / Jarvis" HA project). Near-zero build cost, directly proves "agentic in-room response" instead of "notification read aloud." Put a room-aware/persona-aware prompt in front of every TTS call today. — *wow: very high, feasibility: very high.*
2. **Explicit head-to-head contrast slide/demo vs. Frigate+LLMVision/Ollama pattern**: same VLM-description capability, but QNet never serializes or transmits the frame — image is inferred and discarded on-device, only text crosses the wire. This is the single clearest, judge-legible proof of "privacy-by-construction" since it's comparing against a real, well-known open-source baseline the crowd/judges may already know. — *wow: high, feasibility: very high (just a slide + a log-diff demo).*
3. **Privacy-preserving cross-room "who's where" thread using coarse semantic attributes instead of re-ID embeddings**, modeled on multicam-reid's Lost/Active Registry state machine but fed by QNet's existing JSON events. Proves the multi-device fabric crux with a stronger privacy story than every real re-ID project surveyed (none of which are embedding-free). — *wow: very high, feasibility: medium-high — needs the state machine + a caregiver-app screen, ~1 build day.*
4. **Downsample-before-VLM latency benchmark, shown live**: measured TTFT at native res vs 720p-downsampled (FastFlowLM's Qwen3-VL data shows ~12x blowup 720p→4K on comparable NPU silicon) — a concrete, judge-facing "Technical 40" number with an engineering decision attached. — *wow: medium, feasibility: very high, ~half a day.*
5. **Escalation ladder for ambiguous/uncertain events** (chime → in-room voice check-in → caregiver phone ping → emergency contact), explicitly framed as answering the HA community's own stated pain point (fall-alarm false positives). Turns "the AI is never 100% sure" from a weakness into a designed, narrated safety feature. — *wow: medium-high, feasibility: high.*
6. **Non-camera audio-only semantic sensor tier** (bark/cry/glass-break/gunshot/snore local classification, à la Seeed's XIAO ESP32-S3 module) as a second sensing modality distinct from vision — visibly proves "multi-modal fabric," reinforces zero-raw-audio-leaves-device. Consider sourcing the actual $10 Seeed module as a demo prop / third-party validation citation. — *wow: high, feasibility: medium (need to source hardware fast).*
7. **UNO Q as GStreamer-native motion/VAD pre-filter, not a vision-inference node** — matches its real hardware ceiling (A53 CPU, GPU, no NPU) confirmed by docs and by the broader Pi-Zero/Pi4-choke pattern in the pet-deterrent builds; wake-on-motion → hand off cropped/downsampled frame to an NPU device. Shows heterogeneous-fabric design intentionality for Innovation/Deployment scoring. — *wow: medium, feasibility: very high — this is just correctly using the hardware, should already be the plan.*
8. **Rolling "what happened while you were out" narrative digest for the caregiver app**, generated purely from the accumulated semantic event log (no new inference), inspired by Frigate's "Review Summary" feature. Cheap, high perceived intelligence, demonstrates agentic synthesis over structured privacy-safe data. — *wow: medium, feasibility: very high, ~2-3 hours.*
9. **Wyoming-protocol-compatible cheap satellite node** ($40-60 ESP32-S3) as a bonus room in the fabric, or at minimum an explicit "protocol-compatible with the existing open voice ecosystem" claim — strong Deployment-score (20 pts) evidence of a real-world adoption path beyond the demo kit. — *wow: medium, feasibility: medium (only if spare hardware/time exists — otherwise just cite it).*
10. **Stove/appliance-left-unattended and chore-photo-verification event types**, both trivial additions to the existing semantic-event taxonomy (no new ML capability, just new prompts/labels on the VLM tier already built) — good low-risk breadth-of-scenario padding for the demo reel, one serious (elder safety) one lighthearted (kid chores) to show range. — *wow: low-medium, feasibility: very high, fill-in material.*
